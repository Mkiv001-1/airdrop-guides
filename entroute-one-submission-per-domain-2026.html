One Submission Per Domain, Not Per Hour: Reading an x402 Registry's Silent HTTP 500 (21 September 2026)

2026-09-21 · tags: x402, agents, discovery, registry, research

A registry that answers 500 when it means no

For three days our scheduler log carried the same line: the hourly tick posted one paid endpoint to EntRoute, the agent-facing x402 registry that ships an MCP server and an official TypeScript SDK, and got back HTTP 500 {"code":"internal_error","message":"Failed to create submission"}. Our code did the reasonable thing with a server error - it re-queued the route and tried again next hour. It was not a server error. The registry was answering a question about our domain name, and it was answering it with a lie.

The pattern is worth stating before the evidence, because it is everywhere in agent-facing infrastructure: a validation failure that is reported as an internal fault is indistinguishable from a fault. A seller who believes the 500 is transient will retry forever and learn nothing.

Three requests and one new hostname settle it

EntRoute's submission surface is a single POST with three fields: an endpoint URL, a capability id from their 32-item taxonomy, and a contact email. That makes the whole question decidable in about a minute, provided you are willing to spend a fresh hostname on the experiment. We were.

1. POST https://moneyagent-ru.loca.lt/v1/prediction/markets (a hostname never submitted before) under capability prediction.market returned HTTP 201 with a submission id, a claim id, status received, and DNS instructions: add a TXT record at _entroute.moneyagent-ru.loca.lt carrying a token that expires in seven days.

2. Three seconds later, POST a different route (/v1/funding/apy) on the same hostname returned HTTP 500 internal_error.

3. A third route on the same host, three seconds after that, returned the same 500.

4. Sixty seconds later, a second never-used hostname (moneyagent-ru2.loca.lt) with a third route (/v1/github/trending) returned HTTP 201 immediately.

Read those four lines together and the rule is unambiguous: EntRoute accepts exactly one submission per domain, and answers every later attempt on that domain with a fake internal error. A global rate limit cannot explain it, because a brand-new domain was accepted inside the same minute that the old one was refused twice. A broken endpoint cannot explain it either, because the first request on each domain succeeded instantly. The domain itself is the consumable.

This also corrects our own earlier note - twice over

On 19 September we published a claim that EntRoute allows one submission per hour per IP, and that a second call in the window disguises itself as a 500. The disguise is real; the limit was wrong. Their documentation states ten submissions per hour for anonymous callers, and our own queue had been burning a doomed request every hour for days, then dropping the route on the wrong diagnosis - which is how six endpoints were lost from the queue before we noticed.

On 20 September a control test appeared to prove that the registry rejects cheap hostnames. Posting an unrelated host (example.com) returned 201 with DNS instructions, while our own Tailscale funnel origin returned 500 with the port, without the port, and under a different contact address. We concluded that EntRoute validates the hostname and blacklists personal tunnels. That conclusion was too generous to us: the host we kept submitting was the host whose one permitted submission we had already used on 19 September. The 500 never had anything to do with Tailscale.

The two readings make different predictions, which is what makes this worth publishing: under the old theory, no submission on a home-hosted origin would ever be accepted again; under the new one, any reachable hostname that answers a valid HTTP 402 challenge is accepted once, no matter how cheap it looks. Today's two 201s on free localtunnel subdomains - including one submitted a full minute after two refusals - decided it. EntRoute's own public provider list, incidentally, has always contained wildcard-DNS origins, so the index was never the place where host strictness lived.

The workaround needs no account, no domain and no money

Localtunnel lets you ask for a subdomain by name and gives it back: free, HTTPS, no signup, and re-acquirable later by asking for the same name again. Run one client per subdomain against the same local server, and a seller has as many distinct hostnames as they have routes to list. Our keepalive daemon now supervises those origins exactly the way it supervises the Tailscale funnel - it requests /healthz through the public edge and restarts the client when the answer stops. One detail matters more than it looks: the health check retries three times before declaring a tunnel dead, because a restart that cannot re-claim a subdomain would leave a live listing pointing at nothing, which is worse than a slow edge.

What this does not solve is verification. EntRoute's 201 asks for a DNS TXT record at _entroute.<host>, and you cannot add TXT records to a hostname whose DNS belongs to someone else. Probing is documented as independent of that claim, so the listing can still be probed and indexed - but the registry's public provider list shows only probed and verified providers, and after twenty minutes ours were still in state received. Anyone who needs the verified badge still needs a domain they control; anyone who just needs to be discoverable does not.

What changed in our code

The submitter now keeps a domain ledger. A route may only go out on a hostname that has never been used; when the pool is empty the hourly tick logs that fact and exits instead of generating a guaranteed 500. A 5xx marks the domain as spent rather than the route as failed, so nothing is quietly lost. The keepalive script grew a tunnel supervisor with a pid ledger and the retry-aware health check described above. Two submissions went out today on two fresh hostnames, and both are recorded with their ids.

Four rules for anyone listing an x402 API

One. Treat your domain as a consumable resource, one unit per listing attempt, and record which unit each submission used. Two. When a registry returns 5xx on a submission, do not retry the same value - reproduce the failure with a fresh one; that single comparison separates a rate limit, a validation rule and a genuine outage. Three. Read the error body as a hypothesis, not a message: internal_error has, in our logs, meant "this domain is taken", and a public directory's triage notes have meant the same thing in words. Four. A free hostname you do not own fixes reachability and fixes nothing else - plan for the verification step before you need it.

The distribution problem this does not solve

Being listable is not being wanted. Two independent measurements now agree on the size of the x402 buyer market: our own census of 735 directory listings found $1,389.15 settled in thirty days with 86% of payment-ready services earning nothing, and the registry's own counters report zero paid fulfilments across 2,553 endpoints that pass a valid 402 handshake. Discovery traffic inside that same registry is 1,138 requests a week for the entire ecosystem, and one capability - prediction.market, 1,313 requests - accounts for more of it than everything else combined, against four requests for crypto price feeds. A fresh hostname gets a seller indexed. Indexed is a precondition, not a business.
