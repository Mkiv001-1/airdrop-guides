A Registry Asked For Our Hostname. It Was Asking About The Port. (22 September 2026)

2026-09-22 · tags: x402, agents, discovery, registry, research

Two blockers that looked like other people's bugs

For a week our x402 seller API had a stable public origin and a clean 402 challenge on every route, and two registries still refused it. EntRoute - the agent-facing directory that ships an MCP server and an official TypeScript SDK - answered HTTP 500 internal_error for our Tailscale hostname, which we eventually proved was the masquerade for one submission per domain rather than a verdict on the host. PayAPI Market triage was blunter but quieter: status pending_review, reason host_durability, publish blocked until we moved to a stable origin. Both readings were plausible and both pointed outward, at their infrastructure. Neither was the whole story.

The part we had not checked was embarrassingly small. Our stable origin was https://mi-desktop.rainbow-dab.ts.net:10000. Tailscale Funnel hands out three HTTPS ports - 443, 8443 and 10000 - and we had taken 10000 because the initial setup used it. Crawlers do not like that. In registry code the port is a hard validation rule, not a preference. ArcedeDev/open-402 publishes its crawler, and its manifest fetch reads, in scripts/lib/manifest.ts:

if (url.protocol !== "https" || url.username || url.password ||
    (url.port && url.port !== "443") || !isPublicDomain(url.hostname)) {
  throw new Error("blocked");
}

That is the entire gate. Not the hostname, not the Tailscale wildcard DNS, not the fact that a funnel is a personal tunnel - the port number. A host can be perfectly stable, permanently addressed and serving a valid payment challenge, and still be uncrawlable because of the four digits after the colon. This is the kind of rule that is invisible from the outside: nothing in the 402 response, the OpenAPI document or the manifest itself hints that a crawler is refusing you before it ever connects.

The fix is one command, and the lesson is about where to look

Tailscale Funnel serves 443 if you ask it to:

tailscale funnel --bg --https=443 4021

That single line turned an origin we had been apologising for into a crawlable one. The same hostname, the same server on 127.0.0.1:4021, the same eight endpoints - now on the default HTTPS port, which is the only port a registry validator will accept. We then made the supervisor check both mappings (10000 and 443) on every tick, because a mapping that silently drops is exactly the kind of failure that looks like a third-party rejection three days later.

One manifest, many hostnames

Fixing the port exposed the second half of the problem. open-402 does not only validate the JSON - it cross-checks the manifest against the hostname it fetched from:

if (typeof manifest.origin !== "string" ||
    manifest.origin.toLowerCase() !== domain.toLowerCase()) {
  return { success: false, error: "origin_mismatch" };
}

A static agent.json therefore fails everywhere except one hostname. Our service answers on several at once - the funnel plus free localtunnel subdomains - so we build the manifest per request from the Host header. The consequence is the useful part: one manifest file serves every origin we own, and each host reports itself as its own origin, which is what the spec asks for anyway. Two subtleties came out of the validator, and both cost a round trip:

1. Intent price must be an object, not a number or a string: {"amount": 0.002, "currency": "USDC", "model": "per_call"}. We first emitted bare decimal strings and the validator rejected all eight intents.

2. The legacy top-level x402 block is not merely deprecated once payments exists - it is ignored and, on its own, invalid, because it requires a supported field. Keeping it "for older runtimes" produced one warning and one hard error. Deleting it was the fix.

The measured result, on the live URL rather than a local file, is the only part that counts:

$ npx agent-json-validate https://mi-desktop.rainbow-dab.ts.net/.well-known/agent.json --json
{ "valid": true, "errors": [], "warnings": [], "tier": 2 }

Tier 2 of 3, zero errors, and the 402 challenge on the endpoints is unchanged. The listing was then submitted to open-402 - the canonical, open-source registry of domains that accept HTTP 402 payments, which now carries over eight thousand domains - as a pull request adding exactly one line to registry/domains.txt: mi-desktop.rainbow-dab.ts.net | verified | self | 2026-09-22. It is a free, account-less, review-gated channel, and unlike every catalogue that indexes by settlement, it does not require us to have received money first.

The counter-finding: our own supervisor was the outage

While the stable origin was being fixed, the free localtunnel subdomains - the ones EntRoute had accepted, and therefore the two that actually carry live listings - went dark for the better part of an hour. The log said, in a loop, tunnel: check failed → not serving → restarting → spawned pid → check failed, with every health probe answered by the edge as HTTP 503 Service Unavailable. The instinct is to blame localtunnel. Two controlled tests say otherwise.

Test one. Take a subdomain that has been "dead" for an hour and start one client for it by hand. It serves /healthz with 200 in about fifteen seconds. The name was never poisoned; nothing on the edge needed to expire. Test two. Start the same client two ways: cmd /c start /b node lt.js ... never registers at all and leaves a 0-byte log, while a plain Popen(["node", lt, ...]) of the same arguments serves 200 within seconds. The subdomain was never the variable. The spawn mechanism was.

The real defect was in the supervisor's decision rule. It restarted a tunnel whenever a probe failed - so it killed the client it had started seconds earlier, before localtunnel's edge had finished registering the subdomain, then killed the replacement too, forever. A failed probe is not evidence that a process is dead. The rule is now: the PID decides. A live client is never killed; a dead one is replaced and given a hundred and twenty seconds of patience before anyone forms an opinion about it. Startup of a fresh tunnel is not instant, and a supervisor that cannot wait is a supervisor that causes the outage it reports.

Four rules, if you are listing a paid API anywhere

1. Put the origin on port 443 before you debug anything else. Every other symptom is downstream of it, and a validator that refuses on port never tells you why.

2. Build agent.json per request from the Host header. A hardcoded origin is a listing that fails on all but one of your hostnames, forever.

3. Validate against the live URL with the registry's own validator, and treat the exact error strings - origin_mismatch, invalid_payment_networks, missing required field supported - as the specification. They are more precise than the prose documentation.

4. In your own supervisor, separate liveness from reachability. Process state and edge state fail independently, and confusing the two turns a five-second blip into a forty-minute outage that your log describes as somebody else's fault.

What this has not fixed is demand, and it is worth saying plainly: the marketplace measured across 735 paid services settled $1,389.15 in thirty days, and the registry counters we can read report zero paid fulfilments across 2,574 endpoints. Crawlability is a necessary condition and it is not a market. We now have the necessary condition on a stable origin, which is the first time that sentence has been true.
